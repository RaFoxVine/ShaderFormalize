# Shader 等价验证：目标与选材审阅稿

日期：2026-10-24。状态：范围与选材讨论，尚未确定工具链和实施方案。

本文是当前审阅入口。请直接在 Markdown 中修改或添加评论；反馈完成后，agent 先保存完整的用户修改，再另写修订版。后续不再使用 Lavish。

## 我们要做成什么

输入两份整理前后的 Shader，以及它们共同遵守的输入条件。工具将两份程序转换为适合数学推理的表达，再由 agent 编写证明，交给形式化证明系统检查。检查通过后，可以确认：对所有满足条件的输入，两份程序在约定的实数模型下产生相同结果。

例如，一份程序返回 `lerp(a, b, t)`，另一份返回 `a + (b - a) * t`。转换程序负责明确两边各自表示什么计算；agent 负责解释并证明两个计算相等；证明系统负责检查这份证明是否成立。这里不是让 agent 看完代码后只给一句“等价”。

先验证两份手工整理的代码。怎样自动整理、怎样判断代码更易读，留到之后确定。数学等价也不同时承诺 GPU 性能更快。

## 已确定的范围

- 按实数解释数值计算，不处理浮点舍入、NaN 等问题，也不建设浮点验证模式。
- 普通 Vertex、Fragment 是目标；不做 Compute、wave/shuffle、并发竞争和外部 Buffer 写入。
- 两份程序的输入和 layout 按相同约定使用；有不一致就报错，不建设反射推断和自动重绑定系统。
- 输入允许附带范围或关系条件，例如颜色分量在 `[0,1]` 内、向量长度为 1。范围外的输入不在保证内。
- 证明主要由 agent 完成。自动求解、自动发现证明和自动反例搜索都不是首期交付的必要条件。
- Shader 语言尚未决定。HLSL 是候选，Slang 也是候选，先寻找接入成本合理且能跑通的组合。
- 优先使用已有 Unity 6.5 工程。出现具体环境阻碍后，再评估是否需要升级。

实数运算仍有定义域。例如 `x / x = 1` 需要 `x ≠ 0`。证明必须带上实际需要的条件；agent 不能为证明方便自行缩小用户约定的输入范围。整数除法和位操作也不能直接改解释成实数运算，相关支持范围在选材试验中明确。

## 推荐的工作链：转换程序、agent 和证明系统各做什么

```text
整理前 Shader ─┐
               ├─ 编译器提供的程序结构 ─ 转换程序 ─ 两份数学程序
整理后 Shader ─┘                                  │
输入条件 ──────────────────────────────────────────┤
                                                   ▼
                                            agent 编写证明
                                                   │
                                                   ▼
                                            Lean 检查证明

相同的两份 Shader ─ 运行接入 ─ Unity 实际运行与回归测试
```

“编译器提供的程序结构”就是编译器读懂代码后得到的机器可读取信息。例如 `a = x + y` 会包含：这是赋值、右边是加法、两个操作数是谁、各自是什么类型。我们希望复用这些信息，避免自己重写 Shader 语言的解析和类型检查。

语法树（AST）是这种信息的一种表示：把赋值、加法、函数调用等组织成树。上一版提到的 `ASTConsumer`、`RecursiveASTVisitor` 只是 DXC 内部读取这种树的接口名称，不是用户需要理解的系统组成，也不是已经确定必须使用的方案。

转换程序负责把选定表示解释成数学计算，并保留输入、分支和输出的对应关系。转换本身应由确定性程序完成，不依靠 agent 临时猜测源码含义。agent 在生成的数学对象上写证明；Lean 是目前建议的证明检查器，负责接受或拒绝证明。现有 mathlib 数学库可以帮助 agent 完成代数化简等推理，不需要我们先开发通用自动证明器。

本阶段不为编译器常量折叠或激进优化开发专项恢复机制，也不把上一版的大数常量例子当作选型的一票否决。选择提取位置时一起考虑可获得的信息和接入成本。原目标仍是 Shader 源程序的实数模型等价；如果某条便宜路径只能证明编译后表示，就明确列出保证变化，回到审阅，不默默把两者当作同一个结论。

## 为什么纹理、ddx/ddy、clip 还需要约定

这部分要回答的是：不处理浮点精度以后，剩下的 Shader 操作究竟按什么规则比较。

对于纹理采样，可以先把纹理和 sampler 当作两份程序共同使用的外部环境。如果两边送入同一采样操作的完整参数相同，就能推出采样结果相同。例如证明整理前后的 UV 计算相同后，不必再实现一次 GPU 的过滤器。这能支持一类有用的整理，但不承诺自动证明所有“不同 UV 恰好采到同色”的情况。

`ddx/ddy` 的结果还用到了相邻像素的值，因此不能只把当前像素的一个数送进普通函数来理解。简单例子：一行相邻像素的 `x` 分别是 1 和 2，`ddx(x)` 为差值 1，`ddx(x*x)` 为差值 3。证明时需要保留这种相邻关系；不需要把它升级成 Compute 的线程竞争系统。普通 `Sample` 的 LOD 也会用到像素邻域信息。

`clip/discard` 决定像素是否留下。比较两份 Fragment 时，既要比较相同输入下是否丢弃，也要比较保留时的输出。首个可运行样例可以不同时带齐这些操作，后续再按实际 Shader 用例逐项加入；哪些组合支持、哪些尚不支持，要明确报告。

## 工具选材：现在确定什么，还要调查什么

目前建议保留 Lean/mathlib 作为证明检查侧的优先候选；源语言、编译器和转换实现语言尚未锁定。若最终需要使用某个编译器的 C++ 内部接口，再据此选择 C++，而不是现在先规定整个项目用它。

| 组成 | 候选与用途 | 下一步需要得到的答案 |
|---|---|---|
| Shader 语言与前端 | HLSL/DXC、Slang | 哪个能以更低成本取得足够的程序结构，并让同一案例在 Unity 侧运行？ |
| 数学程序与证明 | Lean 4、mathlib | 能否把提取结果稳定地送入 Lean，让 agent 完成一对简单程序的受检证明？ |
| Unity 接入 | 用户已有的 Unity 6.5 + HDRP 项目 | 已配置的 Unity CLI 如何调用？候选语言如何进入现有 Shader 编译和运行流程？ |
| 自动求解与反例 | 暂不作为必需组件 | 若真实案例证明时有明确帮助，再单独引入，不影响首个闭环成立。 |

对 HLSL/DXC 与 Slang 使用相同的选材标准：取得程序结构需要多少自研工作；常见表达式和类型信息是否够用；agent 写证明是否方便；Unity 接入是否直接；是否引入了需要额外审阅的保证变化。Slang 不是只在 DXC 失败后才看的备胎，也不预先断言它更好。

上一轮已经实际运行过一个 DXC 小样，确认它能输出加减表达式的语法树。这只是局部证据，尚没有做完整的结构化导出器，也没有做 Slang 本地试验或 Lean 端到端证明。

## 你问到的两个术语

**SMT 是什么？** 它是一类自动约束求解方法。比如给出 `0 ≤ x ≤ 1`，再问“是否存在一个 x，使整理前后结果不同”，求解器尝试回答这个问题。Z3、cvc5 是这类工具。它们能辅助 agent，但按这次反馈，我们不把它们及其与 Lean 的对接列为首期必需工作。本文的主要工作链不依赖 SMT。

**SSA 和 lean-mlir 是什么？** SSA 是一种记录程序计算的方式，每次赋值使用一个新名字。例如先写 `a = x + y`，再写 `a = a * 2`，可以记作 `a0 = x + y`、`a1 = a0 * 2`，这样更容易追踪每个值来自哪里。lean-mlir 是在 Lean 中研究这类程序表示及其改写正确性的项目。它可以参考，但不是已经支持 Shader 的现成验证器，也不是目前必须接入的依赖。

## 后续工作与完成结果

先调查并试验一条可行路径，再建立完整闭环，之后扩展普通 Shader 功能。这一推进顺序得到了用户认可；当前的具体工具链与开发范围仍在审阅中。

| 顺序 | 做什么 | 应当交付什么 |
|---|---|---|
| 先选能跑通的组合 | 比较 HLSL/DXC 与 Slang 的结构提取、Lean 接入和现有 Unity 接入成本 | 有证据的推荐组合，说明实际验证到哪一步、还有什么未知 |
| 打通一个小案例 | 两份手工整理的 Shader 转成数学程序，由 agent 写证明，再在 Unity 运行 | 可重复执行的受检证明与运行案例；不是仅手写两条脱离 Shader 的公式 |
| 支持普通计算 | 按真实用例加入向量、矩阵、函数、分支和有限循环 | 明确的支持范围、正确的失败报告、对应的证明与运行样例 |
| 加入 Shader 操作 | 逐步支持纹理、ddx/ddy、简单 clip 等 | 环境约定和受检证明规则，以及能够运行的对应案例 |
| 后续再谈自动整理 | 从用户认可的前后代码中提炼规则 | 独立审阅整理规则及其与验证器的关系 |

这些工作需要完成的产品责任包括：输入条件与接口检查、程序转换、数学定义、agent 可使用的证明入口、证明检查结果报告、Unity 运行接入，以及验证转换与证明链本身的样例。自动发现反例、通用自动证明搜索和编译器优化恢复不在必需交付内。

证明没有通过时应报告“尚未证明”，不能直接称为“不等价”。遇到不支持的语法或操作则报告不支持；若 agent 找到实际反例，可以附带提交，但不要求先建设自动反例搜索系统。
