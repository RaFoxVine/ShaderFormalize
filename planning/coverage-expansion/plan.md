# 语言覆盖、浮点数与 Compute 扩展提案

本文件给项目使用者和后续实现 agent 说明下一阶段要解决什么。2026-10-26，基线为 `77a19da`；这是待讨论的扩展方案，未改变当前实数模型、依赖锁或证明保证。当前已实现内容仍以 README、docs 与现有验收证据为准。

## 目标与实际缺口

目标仍是：输入两份手工编写的 HLSL，生成各自的 Lean 定义和完整待证命题，让 agent 尝试证明等价。核心不依赖 Unity。扩展目标包括常见语言与数学运算、真实浮点运算，以及现代渲染中的 Compute 读写和同步。

本轮四个最小 Shader 均经本地固定 DXC 接受，当前 shared 转换器却拒绝 `min`、`max`、`sqrt`、`/`。`normalize` 内部使用除法和平方根，并不表示导入器接受这些源码写法。[机器调查记录](investigation.json)保存诊断和基线；这轮没有修改产品代码，也没有重复运行已有 213/57 验收。

[覆盖清单](coverage.csv)包含微软常用 intrinsic 表 132 项、SM6.0 Wave/Quad 表 24 项，以及 47 类运算符、语句、类型、资源和执行能力，共 203 行。它是首份名称/能力族目录，不是完整 HLSL 标准、全部重载或覆盖率。逐项实现前，仍要细分参数类型、向量宽度、重载、语言/Shader Model 和语义模式。官方工作草案与提案不自动成为固定 DXC 的现有能力。

## 责任划分

DXC 继续负责 HLSL 解析、类型检查、重载解析和输出定类型语法树。我们的前端负责把已经确定类型的操作、控制流和访问转换为受支持的中间表示，遇到未知节点明确拒绝。公共的操作目录应连接输入类型/重载、内部操作、语义定义、定义域或安全义务及相应验证，避免函数名称分散在多份白名单里却支持范围不一致。

数值语义层负责每种值和运算的含义；片元/Compute 执行层负责调用、条件执行、输出及内存效果。Lean 生成器把这些定义和实际执行的安全义务组成目标，检查器绑定本次输入、语义版本和证明并保持公理审计。有限求值器和 GPU 测试提供反例或实现交叉检查，不代替证明。DXC 和转换器本身目前仍属于可信边界。

## 数值语义：保留实数，增加明确的浮点模式

实数模式继续支持忽略舍入的数学整理；新增浮点模式验证考虑舍入的程序。模式必须显式记录在生成目标和结果中，不能把已有实数证明重新标成浮点证明，也不能在同一数值流中悄悄混用两种含义。

建议第一个浮点参考模型采用 binary32、固定舍入规则和精确 32 位整数，明确每个操作的 NaN、无穷、带符号零、次正规数以及位转换行为。整数沿用/扩展现有 BitVec，不以无限精度整数替代固定宽度。`asfloat`/`asuint` 是位解释，数值类型转换另行定义；要覆盖所有 32 位模式的往返。

NaN 可以作为正常模型值存在，不必要求每个 Shader 都证明无 NaN。默认建议比较可观察输出的完整位模式，HLSL 的 `==` 则另外按它自己的语义计算。原因是 `asuint` 能观察 +0/-0 和 NaN 的编码；“两边都是 NaN”不足以说明后续位运算相同。若以后允许忽略 NaN payload 或零符号，必须限制可观察操作并证明该等价关系在那些操作下保持，不能直接全局替换。

“出口没有 NaN 就说明中间没有 NaN”不成立：比较、条件选择、min/max 可以消去或掩盖 NaN。微软的 Direct3D 浮点规则明确给出相关行为。NaN 不存在性可以是额外性质；等价验证比较两边完整程序的结果与合法性。

模型定义能复用，但证明难度会变化。例如 round-to-nearest-even binary32 下，a=16777216，b=1，c=-16777216，`(a+b)+c=0` 而 `a+(b+c)=1`。原本实数中可用的结合律不能用于该模式。调查记录里的 Python struct 结果只是具体反例，没有冒充 Lean 或 GPU 证明。

IEEE 参考模型也不能直接代表所有 HLSL GPU 执行：需要另外固定目标 API/Shader Model、编译选项、融合、次正规数处理，以及近似运算的规则。未确定的操作可以先作为双方共享的操作参数，只证明在相同解释下的等价；不得把这种结果报告成确定 IEEE 算法或跨设备保证。NaN payload 选择也要显式建模。最终产品目标是可验证的 HLSL 数值配置，参考模型只是第一步。

优先隔离评估 FloatLib，并以 FloatSpec 为对照候选；详见[复用调查](research.md)。两者当前要求的 Lean 版本均高于本仓库 4.24。评估目录和工具链留在本工作区，固定来源、提交和许可证，不升级现有依赖锁。只有构建、公理/证明缺口检查、语义核对及边界测试通过后，才提出正式接入与版本迁移方案。库的 README 声明不是我们的独立验收。

## Compute：从初始内存到最终内存

Compute 的输入包括初始资源内容、资源绑定/布局、dispatch 大小和线程标识；输出是执行后的可观察资源内容。多个 Store 可以自然表示多个输出，但需要保留未写位置的初始值、同线程写入顺序和读写关系。

首个可运行子集包括 `numthreads`、uint3 dispatch 标识、多只读 Texture/StructuredBuffer Load，以及 RWTexture/RWStructuredBuffer 的独立输出写入。以两份输入、两份输出的后处理为首例，包含边界 guard 和不同的索引组织。范围、别名和启动尺寸必须来自用户显式契约；地址合法性、跨线程写/写和写/读冲突不存在应由完整目标证明，不能假定“每个线程只写一次就一定安全”。同线程对自有位置的有序更新可支持，跨线程冲突不能靠任意顺序顺序化掩盖。

随后引入 groupshared 和 barrier：按同步点分阶段，明确跨阶段保存的线程局部状态、共享状态、所有权转移、屏障到达一致性和阶段不变量。再支持原子操作与相应作用域/次序。出现合法但非确定性的执行时，应比较允许的可观察行为或明确精化关系，不能继续假装一定只有一个函数输出。Wave 操作留待相应执行契约明确后推进，不把 Compute 永久限制在逐元素计算。

这条路线不要求首先模拟物理 GPU 的缓存或 warp 调度。可以借鉴 VerCors 的访问权限和同步推理、官方内存关系，但 CUDA/PTX 的规则不能直接当成 HLSL/D3D 的规则。HLSL 0050 内存/执行模型提案当前仍是 Under Consideration，尚有相互不同的候选方案，不能当作已采用的标准。外部验证器的 PASS 也不能未经证明桥接就算作通过本项目 Lean 内核审计。

## 推荐实施顺序与验收

1. **建立系统的基础运算覆盖**：先补 `min/max/abs/clamp`、除法、`sqrt/rcp/rsqrt`、`length/distance` 的 float 标量/向量重载。沿用实数模式时，需要证明实际执行的除法分母非零、sqrt 参数非负等受限域条件，不能借 Lean 总函数在这些域外的定义声称符合 HLSL。这是实数抽象的适用范围；HLSL/D3D 中产生 INF/NaN 的情形并不因此成为非法源码，之后由浮点模式表达。接入前逐项核实 clamp 参数条件等官方语义。用正常材质和错误改写验证整条 DXC→Lean 路线；所有已支持前端、发射器、有限求值器和旧证明兼容性一起检查。
2. **验证浮点依赖能否承担我们的语义契约**：独立环境中验证加减乘除、sqrt、比较、转换和位往返，覆盖 NaN/±0/±∞/次正规数/舍入边界。SoftFloat 可作有限独立对照；必须有通过当前公理要求的完整证明检查，不能以有限测试代替。正确恒等变换应通过，重结合的上述反例不能获得等价证明。评估结论再决定库与升级范围。
3. **形成共同的语言和资源底座**：补 int32/整数向量、入口参数与多输出、全局初始化及资源接口。一般循环需要不变量/终止处理，不能靠截断次数声称完整支持；switch/break/continue 等按实际目标逐项进入。补齐后返回固定 HDRP/Lit Forward，保留真实剩余缺口；IEEE 不是消除全部前端缺口的捷径。
4. **打通实际 Compute 后处理**：无需等待全部数学函数完成，具备所需共同底座即可接入 Load/Store。两输入两输出例证明最终资源相等并包含内存安全义务；错索引、越界、跨线程读写冲突、隐藏别名必须有负控。Unity/GPU 演示可选，默认核心验收仍独立运行。
5. **推进共享内存与同步**：以分块滤波作为 groupshared+barrier 示例，再以有明确次序/观察契约的原子示例推进。每步先确定目标后端的规则和完整证明目标，再实现，不借过去完成的 overnight 授权扩大权限。

这些步骤是相关依赖的路线图，不是所有工作都必须排成一条长队。基础运算与数值依赖评估可先推进；Compute 依赖它实际使用的语言/资源能力，完整 HDRP 验证与 Compute 应各有明确验收。

当前状态、下一次可授权范围和未定事项统一记在 [tasks.md](tasks.md)。本提案不宣称 IEEE 或 Compute 已支持。
